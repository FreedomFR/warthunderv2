# Naval combat simulation (WWII) — guide for Claude Code

Autonomous WWII naval battle on the Noniv/web-ocean WebGPU engine: 43 ships (6 nations × 5 types, plus the S-30 Schnellboot, the Admiral Graf Spee, the Tade, the Gioberti, the post-war USS Adams, the Alaska-class USS Hawaii (CBC-1 command ship design), the Tirpitz, and six other fits of a ship: `data/variants.js`) built procedurally from
spec sheets, AI-only combat, many cameras, modular damage, procedural sound. No build step is needed to play.

**The owner speaks French: answer in French** (code, comments, commit messages and CHANGELOG are in English; README and TODO in French).
Read `TODO.md` for what is left to do and `CHANGELOG.md` for what changed. The owner asked to push to GitHub after every major change;
work on a feature branch and open the pull request into `dev` (not `main`); once the owner has validated what is in `dev` they ask for it to be put on `main` (a pull request `dev` -> `main`), and they tag the release themselves. Never push to `main` or `dev` directly unless asked to.

## Find your way

- `docs/CODEMAP.md`: **every file of `js/`, one line each** (what it is, size, exports, how many files import it), then the scripts of `tools/` and `test/`. Generated: `npm run map` (a test fails when it is stale, and when a file of `js/` lacks its header comment: the first comment of a file says what it is, keep it true).
- `node tools/codemap.mjs --find word`: the files whose name, purpose or exports contain the word. `node tools/unused.mjs`: exports nothing imports (dead code candidates).
- The table below says which files take part in a topic; `docs/ARCHITECTURE.md` (French) explains how the parts fit together; `TODO.md` what is left, `CHANGELOG.md` what changed (newest first: read the top).
- Lines of the source are long (up to 250 characters): read with `cut -c1-220` or by ranges.

## Run and check

```bash
npm install                 # playwright-core and esbuild: only the tools need them
node server.mjs 8080        # then open http://localhost:8080/ in a WebGPU browser (recent Chrome or Edge)
npm run test:fast           # the quick tests on several processes: about 25 s: run it after every change
npm test                    # every test (models, damage, audio, manual control, air ops, fuzz, battles: no GPU needed) on several processes: under 2 minutes
node tools/runtests.mjs --only audio,ui   # some tests; --list: the tests and their times; --serial: one at a time; --verbose: the output of the ones that pass
npm run check:shaders       # compiles the WGSL with a real WebGPU device (server must be running; from WSL with the Windows Node, see below)
npm run smoke               # browser smoke test, offscreen mode (server must be running)
npm run build               # js/ + index.html -> naval.html (single file, git-ignored: over 90 MB, too big for GitHub; the Pages workflow builds it, so there is nothing to rebuild before a commit)
```

A test that rests on a whole simulated battle is chaotic (any change of a model, of the AA of a ship or of the balance moves the outcome): judge the property over a few seeds and accept one that holds (see `test/homeward.mjs`, `test/airops.mjs`), never pin one seed.

A new test is a file `test/<name>.mjs` (a script that prints `PASS` / `FAIL` lines and exits non-zero on failure) **listed in `test/tests.json`** (the runner refuses a test that is not listed; `slow: true` keeps it out of `test:fast`).

The browser tools (`tools/browser.mjs`) render with software WebGPU (SwiftShader) unless `GPU=hardware`, and use `CHROME=/path/to/chrome`
(default: the installed Google Chrome). On a PC with a GPU run them with `GPU=hardware` (checked on an RTX 3080: about 60 fps, and the
on-screen canvas works too; in software rendering only `?offscreen=1` works, so the tools load the game with it).

**WSL2** (the owner's PC: Debian 12 under WSL2, RTX 3080): Linux Chrome cannot reach the GPU there (Debian's Mesa has no Vulkan-on-D3D12
driver) and silently falls back to SwiftShader. Keep `node server.mjs 8080` in WSL and run the browser tools with the Windows Node, which
drives the Windows Chrome (D3D12) and reaches the WSL server through localhost forwarding:
`GPU=hardware WSLENV=GPU "/mnt/c/Program Files/nodejs/node.exe" tools/smoke.mjs`. `npm test` and `npm run build` stay on the Linux Node.
Software rendering is slow: 10–25 s per frame at 800×450 with the ocean on; add `?ocean=0` for model views (about 10 s per shot).

## Adding fidelity to a ship (the "lot" workflow)

1. Collect free photographs and, above all, a profile / plan drawing (`tools/refs/search.py`, `fetch.py`), note licences, credit them in
   `README.md` and `tools/refs/sources.jsonl`; do not commit the images. The spec positions marked `estimated` were often 10-40 m off.
2. Measure on the drawing (overlay it on the model with `tools/refs/overlay.py`): positions go in the spec sheet (`fractionFromBow`,
   secondary `offsetM` / `heightM` / `baseM`, funnel and mast heights, a `measured` note), shapes in `tweaks.js` (`fb` freeboards,
   `planDeck` / `planWL`, `house.plan`, `decks`, tower `tiers` with `towerF` / `towerY0`, `dir0`, `foremast`, `funnels`, `directors`, `cat`).
3. Gun turrets: add or adjust a family in `mounts.js` (house height and length, trunnion height, barrel spacing, muzzle distance, port,
   barbette height `barb` and superfiring `lift`), then set `mainVariant` / `secVariant`. Real gun houses are low (3-4.5 m).
4. **Check it in metres, not by eye**: `node tools/refs/check.mjs <ship>` renders matte silhouettes (side and plan view) with the cameras
   of `tools/refs/plans.json`, then `python3 tools/refs/silhouette.py <ship> side out/check/<ship>_side_render.png` (and `top`) prints
   the mean / worst difference with the drawing station by station, above and under water, and writes a picture (red: only on the
   plan, blue: only on the model). Check each drawing's scale against known depths first (the Yamato profile is drawn 10 % flat:
   `vscale` in plans.json). `stack_top.py` puts the plan view above a top view of the model (AA, boats, turrets).
   Light AA (`aa`), boats (`boats`), screws / rudders / keel / bulb, conning tower, bridge wings and rails come from the plan too; only
   the machinery rooms (spec `machinery`) are from published descriptions.
5. Compare with the photographs from the same angles (`views.mjs` + `shots.mjs`), then film the salvo with the `firetest` scene
   (`--q mount=A`, `--q group=sec`). Add a livery in `livery.js` if needed.
6. Run `npm test` and `npm run check:shaders`, update CHANGELOG / README credits, commit.

## 3D reference models given by the owner (`modelTmp/`)

The owner drops glTF models (Sketchfab, War Thunder "Ninth Wave", CC BY 4.0) in `modelTmp/` (git-ignored). They are **for measuring only**: extract them to `refs/<id>/src` (git-ignored; `python3 -c "import zipfile..."`, there is no `unzip`), measure with `node tools/refs/gltf.mjs` (it also reads a Wavefront `.obj` placed in `refs/<id>/src/` instead of `scene.gltf`; a zip may hold another zip: extract both) (`survey`, `views`, `quarters`, `plan`, `tables`, `cut`, `heightmap`, `profile`; `--loa=` scales the model to the spec's length), build the ship procedurally (spec sheet + `tweaks.js`, never a copy of the mesh), credit the author in `docs/CREDITS.md`. Research guns, shells and torpedoes on the internet (NavWeaps...) for the spec sheet. Then check the model: `tools/refs/chk.sh <ship>` (silhouettes in metres, from the plans.json entry that `gltf.mjs plan ... | python3 tools/refs/addplan.py` writes), and **look at it from every side on a plain background**: `GPU=hardware WSLENV=GPU "/mnt/c/Program Files/nodejs/node.exe" tools/refs/studio.mjs <ids> out/studio` (9 views, lit from behind the camera) then `python3 tools/refs/sheet.py out/studio/<id>.jpg out/studio/<id> 3`. `tools/refs/addspec.py <nation> spec.json` adds a spec sheet. Positions read on a grid: `gridview.py` (the label is the fraction at the LEFT edge, it decreases to the right: bow on the right).

## Elements copied from the reference models (the owner's way since 2026-10)

The ships stay **hand-made** (spec + `tweaks.js` + `ships/<id>.js`); baking a whole model into the game gave an ugly mix and was removed. What is copied from a model is **one element at a time**, as a whole object, placed where the model has it. The best source is an OBJ whose **groups are the ship's own elements** (the Yamato v4 in `modelTmp/yamatoV4.zip`: one named group per turret, shield, gun, director, with the part's name as material, e.g. `JGM164_460mm45`): `gltf.mjs bakeraw refs/<dir>/src refs/<dir>/bake --loa= --draft=` (with the group of each vertex; the waterline of that model is y = 0), `catalog.py refs/<dir>/bake` (what is in it, copies counted), then **`groupmounts.py refs/<dir>/bake tools/refs/<id>_groupmounts.json js/game/model/ships/<id>_elements.js`**: for each kind of mount (config: material, min triangles, `split` for guns) it cuts a group into its objects, takes the barrels (the longest thin objects) and the cradles that touch their rear as the GUNS (origin at the trunnion: they elevate and recoil), the rest as the HOUSE (origin at the training axis), measures the rest direction and the place of every copy. `shipbuilder.js` moves the matching mount records to those places and gives them `look: '<ship>/<kind>'`; `mounts.js` (`makeMount`, `mountDims`) draws the model's house and guns with the measured trunnion and muzzle; light AA copies (`t25`) are added from the placements; registry `model/elements.js`. Models without named groups (the KojfDiscord glTF/OBJ ones) can be searched for repeated objects with `instances.py` + `assemble.py` (the 25 mm of the first Yamato). **After every change check that each element stands where the model has it** (`test/elements.mjs` measures it: the placed copy against its group in the model, within 5 cm) **and look at it** side by side (`pair.sh`) from several angles **and at elevation 35** (`?elev=35` on the preview) before showing it; `tools/refs/WORKFLOW.md`.
**A whole ship from such a model (the Yamato since 2026-10)**: `tools/refs/shipgroups.py refs/<dir>/bake tools/refs/<id>_shipgroups.json js/game/model/ships/<id>_v4.js` turns every group that is not a mount into an element of the game (config: rules by material or group name to `static` / `fine` / `part` with its kind, spin or track; `cuts` that take a box out of a big group, e.g. the tower and the funnel out of the central house; propellers left out, the game spins its own); `tw.v4` (`model/v4ship.js`, `applyV4`) replaces the hull and structure, the fine detail and the destroyable parts of the procedural build with them, recoloured with the game's paint (the texture only tells the wood from the paint and the lights from the darks), wrecks = the charred lower third of the real part; the procedural build still gives the hit volumes, the solids and the arcs. Check `pair.sh` side by side (hull, tower, funnel, deck edge) and the preview with `?ruin=1`. Models that are not made of named groups (merged meshes) are not suited to this: use the element copies (`instances.py`) or leave the ship hand-made.
**A model with no named groups** (a `.glb`, or a glTF merged by material): `python3 tools/refs/glb2gltf.py` unpacks it, then `bakeraw` (env `GLTF_MATNAME=tex` names the materials after their textures, `GLTF_DROP=<regex>` drops aircraft, nets, ocean), `bake.py --split=0 --tris=1000000000 --out=refs/<dir>/full_`, and `python3 tools/refs/splitparts.py refs/<dir>/bake [--merge=regex --family=regex --gap=0.04]` makes the groups (`<material>#k`, the connected objects). A model exported mirrored (island on the wrong side) needs `--mirror=1`; the generators flip the winding by themselves. Never pipe `shipgroups.py` into `head` (it stops before writing).
**A model whose materials are merged (the KojfDiscord glTF, the Iowa)**: `splitparts.py` gives its connected pieces; `groupmounts.py` then picks whole pieces round the game's mount records (`layout_match`, `radius_x/z`, `x_range`, `z_range`, `materials`, `gun_materials`, `gun_min_len`, `gun_box` for a barrel welded to its house, `no_cradle`) or finds the copies of one instance by shape (`template`, a window round one instance; the copies are the same pieces at the same places, turned by a multiple of 90 degrees); `claimed.json` keeps those pieces out of the ship (`use_claimed`); write `<id>_shipgroups.json` from `refs/<dir>/layout.json` (`shiplayout.mjs`): the boxes of its `parts` as cuts, `drop` cuts for the `spinners`, `fine` rules by material (the small, many pieces), `min_len` for the hull. Check the model's waterline (the Adams is 6.9 m above its lowest point): compare the deck edge and the height of a gun with the game's.
**An aircraft from its model (since 2026-10; done: the D3A, the A6M, the SBD, the TBF, the Il-2, the Bf 109, the B-29, the B-17, the He 111, the Lancaster, the B5N2, the F6F-3, the Ju 87 and the Ro.43, all painted by the shader)**: the aircraft are drawn like the ships, from the pieces of the model, with the colours of its textures (camouflage, markings and panel lines are the model's own). `node tools/refs/gltf.mjs bakeraw refs/<id>/src refs/<id>/bake --loa=<any>` (`GLTF_MATNAME=tex`), `python3 tools/refs/bake.py refs/<id>/bake --split=0.06 --alpha=1 --rawout=refs/<id>/split06` (small triangles so that the texture is read finely: 0.045 for a small model, 0.06-0.1 for a big one; `--alpha=1` keeps the alpha of the texture: the triangles of the cards of wires and glass are dropped), then **`python3 tools/refs/planegroups.py refs/<id>/split tools/refs/<key>_planegroups.json js/game/model/aircraft/<key>_v4.js [--probe | --measures | --picture=out/planes/<key>.png]`**: it turns the model about the vertical to the game's frame (`axis_deg` / `yaw` / `pca`, the nose found by the piece `nose` or the tall fin), scales it to the real span (or length), puts the origin 0.42 L behind the nose with the engine axis at y = 0, then gives every triangle to a piece by the config's `rules` (a material regex and/or a `box` in that frame) and by place (`wing_z`, `tail_x`): body, tail, wing (wingL / wingR), prop, gear (the retractable one: drawn while down), glass, canopy (painted by the texture, hidden from the pilot's seat), drop. Each piece is decimated to its `budget` (enough for the shape: a fuselage 15-25k, a fin or tail 5-10k; too little and it looks crumpled) and then refined where the paint changes (`refine`, `minedge`, `colthr`: the soft mottling; `fine: [difference, edge]`: sharp edges such as a roundel, followed down to 3 cm; the colour is also tested at the middle of each edge, or a long thin triangle smears its colour along its length): see `tools/refs/d3a_planegroups.json` (`"refine": 1.2, "minedge": 0.12, "colthr": 45, "fine": [75, 0.03]`). `--measures` prints what the sheet of the type needs (wing chords, tail, fuselage sections, canopy, prop radius): put them in `PLANES[key]` (`planes.js`) with `v4: <module>` and `groundY` (the model's wheels, or the game's own gear when the model has it up), and `model/v4plane.js` draws the pieces for the groups of `drawPlane` (the hook and the load stay procedural). Models are often turned by an odd angle and have asymmetric leftovers: `mirror_wings: "L"` rebuilds the right wing from the left one. Look at it with `Q="&alt=40&ord=0&matte=0" node tools/previewshots.mjs plane:<key> out/planes/p "az,el,dist,lookX,lookY;..."` (Windows Node on the GPU), then redo the wiki picture (`tools/wikiplanes.mjs plane:<key>`, `python3 tools/wikishots.py out/wiki wiki/aircraft --planes`). **The paint is the game's, not the model's (since 2026-10-24; the D3A and the A6M)**: the model gives the shape only. A spec with `paint: '<scheme>'` (`planes.js`) has its skin drawn with `MAT.AIRPAINT` (27; the red channel of the vertex = the scheme number) and the shader (`wgsl/ship.js`, `airPaint()` generated from `model/airpaint.js`) paints it from the table: colour of the upper and the lower surfaces (split by the normal, or by a height line on the flanks), black-blue cowling and anti-glare panel, the roundels as analytic discs in the aircraft's frame (measure their place and size on the model with `python3 tools/refs/planepaint.py refs/<id>/split tools/refs/<key>_planegroups.json`), over the same panel lines, rivets and wear as every other skin. In the config of the aircraft put `"nocolor": ["body", "tail", "wingL", "wingR"]` (the pieces are written without colours) and no `refine` / `fine` (they only served the colours: the triangles drop by half or more, the files by three quarters); give the pieces a budget that is good enough for the shape. Add a scheme to `AIRPAINT` (colours, a `side` colour for a tricolour, `camo` blotches, `mottle`, `finish`, and the markings as `decals` built from discs, stars and rectangles: helpers `usInsignia`, `balkenkreuz`, `redStar`), never read colours from a texture for a new aircraft; a model with no marking in its texture (the Il-2) gets the published size and place, looked at on the aircraft. The propeller and the gear keep their own colours. **Glass is clear** (`MAT.PANE`, drawn blended after the sea and the sky; put the panes last in the builder or leave it to `packMesh`): a model whose panes are transparent in its texture gives them as the piece `glass` (rule with `"clear": true`), one whose canopy cannot be told from its interior gets a `canopyLoft` in its sheet (envelope measured on the model, `v4plane.js`). The pilot's cockpit view is off until the interiors are redone. Pictures: `tools/previewshots.mjs` uses a plain background, a high sun and no clouds (`STUDIO=0` for the game's sky).
**Tools and snags for the next aircraft** (B-17, He 111, Lancaster): `python3 tools/refs/matview.py refs/<id>/split all out.png [tex]` tells the materials apart; `planegroups.py ... --qdump=refs/<id>/q.npz` then `python3 tools/refs/qview.py refs/<id>/q.npz <mats|all> <side|top|front|bottom> <x0,x1,y0,y1,z0,z1> out.png [tex] [px/m]` shows any box of the model in the game's frame (to write the boxes of the rules, the places of the guns and the engines); `origin_nose` fixes where the nose is when what stands beyond the ends (the barrels of the tail guns) is dropped; a rule (`box`) takes the triangles of the materials that the config drops too, so name the material in every rule of a model that holds its geometry twice; the `burn` pieces made by `copies` take the colour of the model (white): put them in `nocolor`, or the propellers of the aircraft show white; `recolor` gives the propeller its black. The pictures of the tools take `BASE=http://localhost:<port>` to look at another checkout.
**Hit volumes**: a ship with `tw.v4` gets `model.hit` (`model/v4hit.js`): shells stop on the drawn surface (`probeDrawn` in `sim/damage.js`), the scar lies on it and has its normal; the mounts keep their own volumes; `test/hitbox.mjs` judges these ships apart.
Done: the Yamato, the Shokaku, the Graf Spee, the Gioberti, the Kagero, the Tade, the Adams, the Iowa, the Richelieu, the Fletcher, the Béarn, the La Galissonnière, the Algérie, the Cleveland, the Baltimore, the Essex, the Fantasque and the Hawaii (see CHANGELOG). Next: the ships the owner gives.

## Acceptance rules for every new ship (set by the owner)

Faithful to the reference as far as it can be measured; **every weapon must work in the game whatever the ship's era** (guns, AA, tubes, aircraft, and missiles / rockets too: a launcher that is only drawn is a bug); the skin, the firing arcs (`tools/audit/arcs.mjs`, `test/arcs.mjs`) and the visuals (nine views, pairs with the reference, wiki picture) checked. Full list: `tools/refs/WORKFLOW.md`.

## Acceptance rules for every new or changed aircraft, weapon or element (set by the owner: apply them every time, without being asked)

These are the same standards as for a ship (above), for anything the game draws or simulates; when an existing element is modified, re-check the list for what the change touches.
1. **Faithful to the reference**: dimensions measured in metres on the model (`--measures`), the shape looked at from every side on a plain background (propeller, glass, gear, bays and loads, no shards, no white or black parts), the wiki picture redone. The paint is the game's (a scheme of `airpaint.js` with the real national markings of the period), never the model's colours.
2. **Every weapon exists, is drawn, and fires**: all the guns of the real fit (count, calibre, rounds, belt, rate), each gun fires from its own barrel on its own line; the fixed guns are harmonised (`FIXED_GUNS` `conv`), every defensive position has its field of fire checked against the aircraft's own structure (`tools/audit/gunarcs.mjs --write` / `--check`, `data/gunmasks.js`), the arcs of ships' mounts likewise (`tools/audit/arcs.mjs`). A gun, a launcher or a load that is only drawn is a bug.
3. **The sim uses the real data, never a flat class figure**: the number of barrels, the calibre, the rate of fire and the **type of round** (mass, filler, incendiary or armour-piercing: `AMMO`, `AA_GUNS`, `data/ordnance.js`) drive the rate of hits and what a hit does (damage, fire, blast). A new gun gets its own entry with its sources (`est` marks a guess), not the figure of the nearest class. A change in the count of barrels or guns must not change the firepower silently: re-measure it (`tools/airtest.mjs`, tests `aadata`, `airguns`).
4. **Flight and handling**: `PERF` with the published figures and their source (`test/flight.mjs` reproduces them), the load, the take-off and the landing (hook and deck, or runway) checked in a short battle; the type is in `ROSTER` / `ROSTER_BASE` of `planes.js` (a carrier or an airfield picks one of the types of its nation by its name), the preload, the wiki and the viewer list it.
5. **Tests and records**: a check for the new element in the matching test (never pin one seed), `npm run map`, `npm test` green, CHANGELOG, `docs/CREDITS.md` (author and licence of the model; "à confirmer" when the file carries none), TODO for what is left; the final report says what was verified and what differs from the real thing.

## Conventions

- Match the surrounding code: short English comments that say why, no model or tool names in repository files.
- Particles are premultiplied-alpha billboards (CPU pool in `render/particles.js`); fire, flashes and tracers write alpha 0 so that they add light.
- Rendering is camera-relative with reverse-Z; keep the NaN/Inf guard of the HDR output.
- Keep `npm test` green; the visual work is judged on rendered frames, so look at them (contact sheets) before claiming a result.
- Do not mention model identifiers in commits, PR text or code.

## Known pitfalls (learnt the hard way)

- **WGSL**: `patch`, `macro` and other reserved words cannot be variable names; `let a = 1, b = 2;` does not exist (one declaration per `let`); variants of a shader are `override` constants set in the pipeline (see `SMOKE_DETAIL` in `wgsl/particles.js`). `tools/wgslcheck.mjs` must run on the real GPU (Windows Node) to catch these.
- **A new material** = a constant in `model/meshbuilder.js` `MAT` + a `case` in the fragment shader of `wgsl/ship.js` (the vertex carries the id in its alpha byte; ids up to 255; `mat <= 5u` tests in the shader mean the ship paints). Check the other tests of `mat ==` before reusing an id.
- **Shell**: a heredoc with backticks needs a quoted delimiter (`<<'EOF'`), or the shell runs what is between them; `pkill -f name` also matches the shell that runs the command; a command over 2 minutes is moved to the background by the tool (poll its output, do not `sleep`).
- **Pictures**: judge them from frames on the RTX (`tools/baseshots.mjs` with the Windows Node), never from the code alone; the sound cannot be heard here: `tools/audiolab.mjs --png` shows a sound's spectrogram.
- **Git**: after a pull request is merged, restart the branch from `origin/dev` (`git checkout -B <branch> origin/dev`) and push with `--force-with-lease`; the PR body is updated with `gh api -X PATCH repos/<owner>/<repo>/pulls/<n> -F body=@file`.
